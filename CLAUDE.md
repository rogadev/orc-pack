# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

`orc-pack` is a **source pack** you integrate into your larger projects — it distributes `/orc` (also callable as `/do`), which works GitHub issues end to end in the main session, plus `/orc-review`, the deep review that runs afterward with a bench of reviewer subagents, and a few supporting skills. It reaches a project one of two ways: installed as a Claude Code plugin (this repo is also its own plugin marketplace), or copied into that project's `.claude/`. Either way the pack runs _inside those projects_, never in place here. There is no application code in this repo: every deliverable is a Markdown prompt (`skills/*/SKILL.md`, `agents/*.md`, and the reference files under `skills/*/references/`) that ships elsewhere. "Editing the product" means editing prompt text, not code.

Read `README.md` for the user-facing behavior and `INSTALL.md` (written for an AI agent) for how the pack gets copied into a target repo.

## Layout

- `skills/orc/SKILL.md` — the build workflow, and the core deliverable. It works one issue, a list, a range, `next N` from the board, or a plain-text request, one issue at a time in the main session: plan, pin the behavior in tests, build, screenshot UI, update docs, commit per issue, then push and close at the owner's word. It dispatches no builders or reviewers; review is `/orc-review`, run afterward in a fresh session. User-invoked only.
- `skills/do/SKILL.md` — `/do`, the same skill under another name: it reads and follows `../orc/SKILL.md`. Keep every workflow rule in `skills/orc/SKILL.md`; this file holds nothing else.
- `skills/orc/references/` — the shared quality bar, read by `/orc-review`'s lanes: `standards/` (code, comments, structure, ui, data), `frameworks/` (next, nuxt, sveltekit, astro), and `platforms/` (cloudflare, vercel). Also `update-check.md`, the once-a-day check for a newer release whose one line ends the reports of `/orc` and `/orc-review`. They carry no `pack:` marker; the release guard and the marker check cover only `SKILL.md` and agent files.
- `skills/orc-review/SKILL.md` — the read-only deep review of a branch or range, which runs only the lanes the change's risk surfaces call for, detecting the stack's playbooks itself. Its `references/profile-template.md` is the project profile that `/orc-review setup` writes to a target repo's `.claude/skills/deep-review/SKILL.md`: repo-owned, never overwritten by an update, and holding only what's specific to that project (stack, checks, platform constraints, risk map, repo lanes, ignore paths, architecture, non-issues, extra focus, and optional after-verification and report-destination steps). Its `references/template-changes.md` holds the **review template** number and, per version, what an existing profile or lane needs (see **Conventions when editing prompts**). Its `references/lane-template.md` is the contract for a repo lane, a project-owned reviewer agent that adds depth where the generic lanes are thin: the same brief in, findings written to the brief's `Report` file and a one-line reply out, read-only otherwise. Keep the review workflow in `orc-review`; a profile never copies it.
- `skills/newissue/SKILL.md` — turns a rough idea into a self-contained GitHub issue; `/orc` uses it when the owner asks it to file one.
- `skills/shipcheck/SKILL.md` — verifies a push through CI, required secrets, the live deploy, and browser smoke checks, fixing a red run or a regression in the main session; optional.
- `skills/retro/SKILL.md` — the read-only retrospective on past `/orc` runs and the reviews after them. `references/usage.mjs` summarizes the session transcripts under `~/.claude/projects/` (cost and active minutes per closed issue, split into build, review, and fix sessions; tokens per agent type; costliest dispatches; retries; tool errors; timelines), and an Opus agent reads that with the saved review reports to find what to improve.
- `skills/tiedown/SKILL.md` — the end-of-session check, user-invoked only and read-only. Stage 1 finds every open question and loose end (or replies "We're done."), stage 2 sizes each item and thinks it through with no subagent, a Haiku, a Sonnet, or an Opus one, and stage 3 presents one decided list the user can approve with a single reply. Optional.
- `skills/update-orc/SKILL.md` — updates an installed pack to the latest release from any older version, dispatching the `orc-updater` agent. Its `references/check-install.mjs` compares an install with a kit checkout file by file (missing, different, repo-owned at a pack name, stale, and personal skills that shadow the project's) and exits non-zero on a gap; `INSTALL.md`, `UPDATE.md`, `/update-orc`, the updater, and `/orc-review setup` all end by running it.
- **The install model:** a target repo's `.claude/` holds the whole pack, identical to the kit, plus what's unique to the project (its review profile, the profile's references, repo lanes, and `CLAUDE.md` facts). A file at a pack name is always the kit's; project knowledge never lives in a pack file. Keep that split when editing the install, update, or setup prompts.
- `agents/*.md` — one file per subagent (the review lanes, verifier, setup-auditor, tooling runners, the vetters, orc-updater). Each has YAML frontmatter: `name`, `pack`, `description`, `model`, and optional `tools`, `effort`, and `memory`.
- `CHANGELOG.md` — one section per released version; the release guard publishes the matching section as the release body, and `/update-orc` reads it as the update map.
- `.claude-plugin/plugin.json` — plugin manifest; its `version` is the single source of truth for releases.
- `.claude-plugin/marketplace.json` — marketplace descriptor.
- `.github/workflows/release-guard.yml` and `pack-integrity.yml` — the CI that enforces versioning, formatting, and pack consistency (see below).
- `INSTALL.md` and `UPDATE.md` — written for an AI agent installing or updating the pack in a target repo.
- `docs/` — maintainer notes that never ship: `model-tiers.md` (the evidence behind the model tiers) and `do-trial.md` (the trial and measurements that made `/do` into `/orc` in 2.0.0).
- `.claude/skills/condense/SKILL.md` — `/condense`, a maintainer skill that never ships. Run it after adding or changing skills, agents, or references: it cuts the shipped prompts to the fewest tokens that keep every instruction, and an independent verifier checks that nothing was lost.

## No build, lint, or test toolchain

This repo has no `package.json`, no local scripts, and no test suite — it is prompt content. Don't look for a `ready` command or a way to "run" the pack locally. The automated checks are two workflows: `release-guard.yml` runs `npx prettier@3 --write .`, does the version bump/sync, and refuses to release a version with no `CHANGELOG.md` section; `pack-integrity.yml` verifies that every `pack:` marker matches `plugin.json`, that every agent a skill names exists, that every skill and agent frontmatter parses, that every standard and playbook `/orc-review` names exists under `skills/orc/references/`, and that the review template's current number has its section. If you want to match what CI will do to your Markdown before pushing, run that same Prettier command; otherwise CI formats it for you on the PR into `main`.

## Versioning is load-bearing — how releases actually ship

Plugin users only receive updates when `.claude-plugin/plugin.json`'s `version` changes. Four coupled facts follow:

1. **Every skill and agent file carries a `pack: orc-pack@x.y.z` marker** in its frontmatter (line 3). The reference files under `skills/*/references/` carry none; install and update docs treat them as pack-owned because they sit in the pack's skill directories. These must all match `plugin.json`'s version.
2. **You normally don't bump or sync these by hand.** The release-guard workflow, on PRs into `main` (and direct pushes to `main`), detects any change under `skills/` or `agents/` that landed without a version bump, bumps the patch version, rewrites every `pack:` marker to match, runs Prettier, and commits the fixes back onto the branch under review.
3. **Every released version needs a `CHANGELOG.md` section.** The guard extracts the `## [x.y.z]` section and publishes it verbatim as the GitHub release body; with no section, the job fails and nothing is tagged or published. `/update-orc` reads that body, plus every section between the installed and target versions, as the map an updater agent follows — so write each entry for a stranger who may be jumping several releases: what changed, the exact files, any migration, and the paths to read.
4. **A released version's section is frozen.** Once `v<x.y.z>` is tagged, never edit its `CHANGELOG.md` section: it is already published as that release's notes, and a later release (for example a `2.0.1` patch after `2.0.0`) gets its own new section. Run `git fetch --tags` and check the tag immediately before editing a section, because the guard can publish a version while you work on `dev`. When the new release follows the last one closely, recap the earlier release's changes in the new section and link its release notes, without copying its update steps.

Practical consequence: when editing skill or agent content on `dev`, you can leave the version alone and let the guard bump it, **or** bump `plugin.json` yourself for an intentional minor/major release — but if you bump by hand, sync the `pack:` markers in the same commit so they don't drift. Never hand-edit a `pack:` marker to a version that disagrees with `plugin.json`.

## Model assignments are intentional

`/orc` runs on the session's own model and dispatches no subagents of its own (it may send a wide search to Claude Code's built-in Explore agent, pinned to Haiku in the dispatch because Explore otherwise runs on the session's model, and runs the `fallow` agent once before its report when the run removed or moved code). Every other agent pins a `model:` and, where the model supports it, an `effort:` in frontmatter:

- **Haiku** (`haiku` alias) — command runners that relay output and make no judgement calls: `lint`, `typecheck`, `test`, `usages`, `fallow`. They carry no `effort:` line: Haiku 4.5 didn't support it, and Haiku 5.5's default (`medium`) is enough for relaying output. The alias follows new Haiku releases.
- **Sonnet 5.5** (`claude-sonnet-5-5`, `effort: high`) — `test-coverage-reviewer` only. Whether logic is tested is a mechanical, recall-heavy question, and the Opus 5.5 verifier filters its false positives.
- **Opus 5.5** (`claude-opus-5-5`) — every other agent, with `effort` as the cost control:
  - `high` — `security-reviewer`, `skill-vetter`, `dependency-vetter`, `orc-updater`: security work, plus jobs that run too rarely for effort to matter to cost.
  - `medium` (Opus 5.5's default) — `verifier`, `setup-auditor`, `quality-reviewer`, `architecture-reviewer`, `ui-reviewer`: the review judgement that decides code quality and design, which is the pack's top priority.
  - `low` — `comment-reviewer`: a narrow rubric.
- **Fable 5.2** — not used. At $8 and $40 per million tokens it costs twice as much as Opus 5.5, and Anthropic's guide reserves it for work Opus 5.5 at `high` still gets wrong. No lane here needs effort past `high`.

Security review and verification stay on Opus 5.5 regardless of cost. Sonnet is pinned to the explicit id `claude-sonnet-5-5` so that moving to a later Sonnet is a decision, not a silent change; Haiku stays on the `haiku` alias because its runners make no judgement calls. Revisit the tiers when the next Opus, Sonnet, or Fable ships, and read `docs/model-tiers.md` first: it holds the evidence, including the pre-2.0.0 builder tiers kept as history. To check a review tier, compare each lane's raised and kept counts in `/orc-review`'s plan lines and saved reports, and `/retro`'s per-issue figures.

Pin Opus in frontmatter as the explicit id `claude-opus-5-5`, never the bare `opus` alias: Claude Code runs an alias subagent on the session's own model when both are in the same family, so an alias would follow a session running on Opus 5. **Opus 5 (`claude-opus-5`, the 5.0 release) stays banned** for running the pack (`/orc` refuses to start on it); don't reintroduce it as a default anywhere. Opus 5.5 is a different model and is the recommended one.

## Conventions when editing prompts

- **The pack is repo-agnostic by design.** `/orc` and the agents discover the target repo's stack, commands, and conventions at runtime by reading its `CLAUDE.md`/`AGENTS.md`, `.claude/rules/`, hooks, manifest, and code. Don't hardcode a stack, command, or path (like `pnpm ready` or a `dev` branch) into a skill or agent — keep it general and let it discover.
- **Stack knowledge lives in the playbooks, not the agents.** Framework- and platform-specific rules go in `skills/orc/references/frameworks/` or `platforms/`, which `/orc-review` loads only when it detects that stack. Each playbook tells agents to check the installed version and to trust that version's docs over the playbook; keep version-sensitive claims hedged that way. Adding a playbook means adding its detection rule to the **Standards** paragraph of `skills/orc-review/SKILL.md` and naming it there by its path (`frameworks/<name>.md`), which is what `pack-integrity.yml` checks.
- **The standards defer to the repo.** Every standards file ranks the repo's own docs and established patterns above itself. Keep that precedence when editing them; the pack is used in client repos whose structure must never be reshaped to the pack's taste.
- **Every agent that reads a standard gets it by path from `/orc-review`**, with a fallback to `.claude/skills/orc/references/` when run on its own. When you add a standard or change which lane reads it, update `/orc-review`'s **Standards** paragraph and lane briefs.
- **The review template has its own version, and it moves rarely.** `skills/orc-review/references/template-changes.md` names the current review template number, which covers `profile-template.md` and `lane-template.md` together. Bump it only when a change would make an existing project's profile or repo lanes read differently or miss something: a new or moved section, a new field, or a changed lane contract. Wording fixes, and changes to `/orc-review`'s own workflow that existing profiles already work with, don't count. In the same commit, add a `## Template <n>` section with a one-line **Summary** and one item per change, each with an id (`<n>.<k>`) and what an existing profile or lane needs, because `/orc-review setup` applies those items and a profile's **Declined template changes** names them by id. Never renumber or edit a released item. `pack-integrity.yml` warns on a pull request that changes either template without touching `template-changes.md`.
- **Frontmatter shape must stay consistent** across files: `name` and `pack` first, then `description`, then `model` and `effort` (an agent's `tools` list may sit between `description` and `model`; a skill's `argument-hint` and `disable-model-invocation` follow `description`). The `description` is what triggers the skill/agent, so it carries the trigger phrases — keep it specific.
- The working branch is `dev`; `main` is the release branch that the guard and plugin consumers track. Open PRs from `dev` into `main`.
